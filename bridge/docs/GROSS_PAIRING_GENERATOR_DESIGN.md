# Gross 固定配对生成器设计

## 当前状态

`js/lehman.js` 现已预存 5×6、6×7、7×8 的双树分解。生产代码在蓝方大师级
开局后使用该计划，不再对这些尺寸执行 Alpha-Beta 搜索；3×4 仍保留手写 Gross
表，用于配对演示和已穷举验证的静态应答。

因此，“已经有通用生成器、无需再验证”的说法不准确。参考资料证明 Gross
配对可以规则化扩展，但 Figure 112 只给出图和简短说明，没有直接给出可复制
的坐标公式。因此运行时实现采用 Lehman 的等价动态形式：预存两棵初始树，而
不是伪造一张不随局面变化的静态回应表。

参考：[Martin Gardner, *Bridg-it and Other Games*, Figure 112](./bookchapter-12.pdf)。

## 配对对象

棋盘不是把任意两条线配对，而是配对交叉位点：

- A 类位点：`rh_r_c` 与 `bv_r_c` 相交，数量为 `R * (C - 1)`。
- B 类位点：内部 `rv_r_c` 与 `bh_{r+1}_{c-1}` 相交，数量为
  `(R - 1) * (C - 2)`。
- 蓝方首步 `bv_{R-1}_0` 会封锁一个 A 类位点，因此剩余有效位点数为
  `R(C-1) + (R-1)(C-2) - 1`，在标准 `R×(R+1)` 棋盘上为偶数。

每两个有效位点组成一组。若一组的两个红方落点是 `redA`、`redB`，其蓝方
回应必须是对端的两条蓝边：

```text
redA -> blueB
redB -> blueA
```

边界红竖线不参与有效连通，可与边界蓝横线单独建立无害回应；这部分不能混
入有效位点配对。

## 生成流程

静态 Gross 表的目标接口可表示为：

```js
{
  openingMove: 'bv_{R-1}_0',
  sitePairs: [{ redA, blueA, redB, blueB }, ...],
  responseMap: { redEdgeId: blueEdgeId }
}
```

若继续实现可视化或离线缓存，生成器分五步：

1. 按棋盘尺寸枚举 A/B 位点，删除开局占用的位点。
2. 按 Gross Figure 112 的平移、交替方向和边界规则生成位点对。这里必须
   使用参数化格点规则，不能复制 3×4 的字面边 ID。
3. 将每个位点对转换成两个方向的 `responseMap` 条目。
4. 为边界红竖线建立一一的边界蓝横线回应。
5. 输出可缓存的 JSON；运行时大师 AI 只需按最后一手红边 O(1) 查表。

## 必要验证

即使数学构造来自 Gross，代码仍需验证坐标转换没有偏移：

- 所有红方键在开局后合法，且每个只出现一次。
- 所有蓝方值合法、未被开局占用，并且不重复。
- 每个回应确实位于同一交叉位点对的另一端，不与红方刚走的边相交。
- 5×6 可枚举 `2^20` 个有效位点取向作为回归证明；更大尺寸使用结构不变量
  检查，并保留少量随机顺序测试作为运行时保护。

当前 Lehman 实现使用的缓存结构是：

```js
{ openingMove, treeOne, treeTwo }
```

两棵树都覆盖同一组收缩后的蓝方顶点，只共享 `openingMove`；它们的并集正好
覆盖所有有效蓝边。红方删除某树的专属边后，代码在另一棵树中寻找跨越断口的
边，将其标记并加入被修复的树。边界步使用一一的边界回应。该过程不进行
Minimax、Alpha-Beta 或 MCTS 搜索。
